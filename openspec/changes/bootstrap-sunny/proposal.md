## Why

Devon wants a personal AI agent ("Sunny") that runs locally on his home server and acts on his behalf: interacting with the machine, building websites, doing research, browsing the web with his credentials, answering email, and handling todos. The primary interface is iMessage, with other channels (CLI, email, Telegram, web chat) added over time.

The architecture is inspired by Nous Research's **Hermes Agent** (its memory model, self-authored skills, durable gateway, cron self-scheduling, bounded delegation, and layered security), but re-implemented on a **TypeScript / Vercel** substrate (AI SDK v6 with Claude Opus, optional Workflow DevKit for durability) rather than forking Hermes' Python.

This change bootstraps Sunny. It is being captured incrementally: subsystem designs are decided in explore mode and recorded here one capability at a time. **All ten subsystem capabilities are now finalized: `agent-memory`, `messaging-gateway`, `durable-execution`, `scheduling`, `security-permissions`, `credentials`, `tool-access`, `agent-skills`, `observability`, and `subagents`.** What remains before implementation is non-capability foundation: the project skeleton / stack conventions, backups, and the `tasks.md` build plan.

## What Changes

- Establish the overall Sunny architecture and substrate decision (TS/Vercel, files-first, self-hosted, direct host access guarded by approval tiers).
- **Finalize and specify the `agent-memory` capability**: a layered memory architecture whose *soul* (capped always-on markdown core + on-demand topic docs) stays in git-able files, with message recall (Postgres tsvector full-text + optional local `pgvector` semantic upgrade) in the DB tier, a nightly self-scheduled consolidation job, and date-tagged facts for temporal reasoning. Reject managed memory services (Supermemory, Honcho, Mem0, Zep/Graphiti) for a single-user, privacy-sensitive, self-hosted agent.
- **Finalize and specify the `messaging-gateway` capability**: a channel abstraction where the agent core speaks one normalized interface and each channel is a pluggable driver. iMessage first, via the Vercel Chat SDK (`npm install chat`) with Photon's `vercel-chat-adapter-imessage` (built on `spectrum-ts`) as the transport on Spectrum Cloud, behind a thin custom `Gateway` seam. Sunny owns its own conversation store (the transport provides no message history). Start on Photon's free tier (1:1 DMs + reactive group participation); keep Sendblue (durable group IDs / proactive group messaging) as a swappable upgrade.
- **Finalize and specify the `durable-execution` capability**: a two-tier execution model on Vercel Workflow DevKit (`@workflow/world-postgres`). Tier 1 conversational turns are idempotent per inbound message (re-process any un-answered message after a restart); Tier 2 long/async jobs run as durable workflows that survive crashes/reboots and resume. No user-facing token streaming (iMessage delivers complete messages), so the streaming stack is skipped entirely. Persist messages once on durable completion (no double-write). Consolidate the message archive, FTS, vectors, and workflow state into one Postgres.
- **Finalize and specify the `scheduling` capability**: Sunny can schedule itself. Schedule definitions (relative/absolute one-shots, intervals, cron expressions) are persisted in Postgres, survive restarts, and dispatch as Tier-2 durable jobs; one-shot delays may use WDK's durable `sleep()`. Includes an anti-recursion guard (a scheduled run cannot create new schedules), gateway delivery of run output, and a per-run cost/rate cap for autonomous runs.
- **Finalize and specify the `security-permissions` capability**: a defense built on the principle that untrusted content (web, email, skills) may hijack the model, so high-consequence *actions* are gated. Identity (only the paired user commands Sunny), balanced "smart" approval tiers with money / destructive / act-as-you actions hard-gated regardless, a hard blocklist always refused, an isolated credentialed browser (other host access direct; skill installs gated), prompt-injection containment (untrusted content is data, not instructions), and audit logging into observability.
- **Finalize and specify the `credentials` capability**: 1Password as the secrets layer via `@1password/sdk` and a read-only Service Account scoped to a dedicated minimal `Sunny` vault (Service Accounts cannot reach the user's Private vault, so creds outside the Sunny vault are unreadable by construction). The LLM never sees secret values — only `op://` references; each tool whitelists the exact references it may resolve; values are resolved in the tool layer, never in model-visible text or logs; the token file is hardened and rotated.
- **Finalize and specify the `tool-access` capability**: Sunny's tool catalog (shell/host, web research, credentialed browser, email, todos, build/host sites) where each tool declares a risk tier and the credential references it may resolve, and the risk tier maps to gating (auto / approval / forbidden) per the security policy.
- **Finalize and specify the `agent-skills` capability**: Sunny installs, writes, and learns its own skills using the `agentskills.io` `SKILL.md` standard (progressive disclosure; files under `~/.sunny/skills/`, git-able). Self-authored skills are created auto-and-notify; externally installed skills are untrusted code, approval-gated and reviewed. Skill actions always pass through tool-access gating, so a skill cannot escalate privilege. Discovery scales from a budget-capped metadata index to pgvector retrieval over descriptions (reusing memory infra).
- **Finalize and specify the `observability` capability**: OpenTelemetry as the tracing standard (AI SDK telemetry + Workflow DevKit execution + gateway/tool spans) exported to a self-hosted local collector (no egress). Persistent per-run trajectory records, a cost/token budget meter that enforces the caps referenced by `scheduling` and `agent-memory`, the redacted audit log referenced by `security-permissions`, and a user-facing insights summary deliverable over the gateway.
- **Finalize and specify the `subagents` capability**: bounded `delegate_task`-style delegation whose primary purpose is context/token preservation — a child runs an isolated subtask with a restricted (subset) toolset and returns only its result, keeping the parent's context lean. Bounded by concurrency and depth caps; subagents run least-privilege (never broader than the parent) and are ideal for isolating untrusted-content processing; a delegated task may itself be a durable Tier-2 job.

## Capabilities

### New Capabilities
- `agent-memory`: How Sunny stores, recalls, and curates what it knows about Devon and itself — the always-on core, on-demand topic docs, keyword/semantic recall over message history, and self-scheduled consolidation.
- `messaging-gateway`: How Sunny sends and receives messages across channels — a normalized gateway interface the agent core speaks, with pluggable channel drivers (iMessage via Chat SDK + Photon first), capability flags per channel, sender authorization, and a self-owned conversation store.
- `durable-execution`: How Sunny runs work so it survives restarts — fast in-process conversational turns made idempotent per message, plus durable Workflow DevKit jobs for long/async tasks, on one Postgres that also holds messages, FTS, and vectors.
- `scheduling`: How Sunny schedules itself — persisted one-shot/interval/cron schedules dispatched as durable jobs, with an anti-recursion guard, gateway delivery of output, and cost caps on autonomous runs.
- `security-permissions`: How Sunny stays safe despite untrusted content — identity, smart approval tiers with high-consequence actions hard-gated, a hard blocklist, an isolated credentialed browser, prompt-injection containment, and audit logging.
- `credentials`: How Sunny holds secrets — 1Password Service Account scoped to a dedicated minimal vault, accessed via the TS SDK, with the LLM seeing only `op://` references and a per-tool reference whitelist.
- `tool-access`: What Sunny can do and how each action is gated — a tool catalog where each tool declares a risk tier and the credential references it may resolve, mapped to auto/approval/forbidden gating.
- `agent-skills`: How Sunny installs, writes, and learns skills — the `SKILL.md` standard with progressive disclosure, self-authored skills (auto + notify) vs untrusted installed skills (approval-gated), all actions gated at execution.
- `observability`: How Devon sees what Sunny does and bounds its cost — OpenTelemetry traces (self-hosted), per-run trajectories, a cost/token budget meter enforcing the caps, a redacted audit log, and an insights summary.
- `subagents`: How Sunny preserves context while doing complex work — bounded, least-privilege delegation that isolates a subtask and returns only its result.

## Impact

- **New project** (`sunny`), greenfield. No existing code or specs affected.
- Stack: TypeScript, Vercel AI SDK v6 (`@ai-sdk/anthropic`, Claude Opus 4.8), Vercel Chat SDK (`chat`), Vercel Workflow DevKit (`@workflow/world-postgres`), Postgres (+ `pgvector` later). Memory soul as files under `~/.sunny/memory/`.
- Memory *soul* is plain markdown under `~/.sunny/memory/` (git-able); the DB tier (messages + tsvector FTS, pgvector embeddings, and Workflow DevKit execution/job state) is consolidated in one Postgres instance.
- Adds an operational dependency on a running Postgres instance and a long-lived worker process (WDK's Postgres world is not serverless — appropriate for an always-on home server).
- Adds a 1Password dependency: `@1password/sdk` plus a read-only Service Account token (`OP_SERVICE_ACCOUNT_TOKEN`, hardened file) scoped to a new dedicated `Sunny` vault the user populates via the 1Password UI. (Native 1Password access auditing requires a Business plan; Sunny's own observability logs tool + secret access regardless.)
- Establishes the security posture: direct host access guarded by smart approval tiers + a hard blocklist, an isolated credentialed browser profile, and the rule that the LLM never receives secret values.
- Post-design review refinements (see design.md → Review Resolutions): group trust = owner-commands/others-context; email via Sunny's own mailbox `sunny@waywardlane.com` (himalaya CLI, CC-to-act); website building via the `devbox` skill (durable public deploy deferred); skill installs via `npx skills`; persistent logged-in browser profile (cookie store protected like the vault); per-thread turn serialization + serialized memory writes; a global spend circuit-breaker + step cap; durable-suspended, id-correlated approvals; Haiku-class smart-mode triage; memory cold-start onboarding. Prompt caching reframed as a conditional (multi-step-turn) optimization, not a blanket cost win.
- Establishes the always-on token budget that every message-handling run pays, so it affects per-message cost and latency.
