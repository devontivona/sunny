# Proposal: unified-voice-layer

## Why

Three production pathologies surfaced on 2026-07-13/14, and they are one disease. (1) Scheduled jobs texted Devon their working notes — a literal `<no-reply/>` token, then "I sent it through the wrong path — let me put it in the final reply instead" glued onto the real message — because the scheduled profile's final text goes to a human verbatim but nothing ever told the model that, and the sentinel parse existed only on the conversation path. (2) A conversation turn answered a subagent's report *through Devon's thread* ("Got it, keep going — I'll create the schedule myself…") because no prompt states that an incoming report's sender is not the reply's recipient. (3) A model-created hourly schedule spams Devon because `schedule_create` cannot express "no delivery expected" — the runtime's silent/household machinery exists but isn't exposed or taught, and the tool description says results are "delivered automatically."

The audit against the specs shows why patching won't converge. `run-audiences` says audience is *pure addressing* and silence is *the absence of a messaging grant*; `tool-access` (the D-RA14 revision) says speech *derives from the audience axis, never a grant*; and the code additionally still carries the retired `outputTarget: user|silent` flag in the DB, the scheduler, and every standing-schedule file — three competing vocabularies for "does this run talk." The spec's "conditional delivery is emergent, not a flag — no empty-message convention" collided with text-as-reply (the final text auto-delivers), which forced the sentinel into existence as a per-profile bolt-on; `messaging-gateway` still documents the pre-#73 strip-and-deliver semantics. And `run-audiences`' "one shell over a RunSpec — prompt framing … derived, not hardcoded per profile" was only half-built: delivery and toolsets are derived and shared, but the *speech contract* (who hears my final text, how to be silent, how to address anyone else) is hand-written three different ways in three prompt builders and parsed three different ways in three workflow files. Every pathology is that missing layer surfacing in a different profile.

There is also a quality problem patches can't fix: a scheduled run composes human-facing prose from a cold context. It cannot see the live conversation, so its texts land mid-thread with no transition, duplicate what was just discussed, and can't exercise judgment about timing — while subagent output, which flows through a conversation turn, reads naturally because the mediating turn has history and voice.

## What Changes

- **One speaker (BREAKING for scheduled delivery).** Only a conversation turn ever delivers text to a human. Every autonomous run — delegated subagent *and now scheduled job* — is a report producer: its terminal text is appended to its audience's conversation thread as an attributed report (`<label> (scheduled): …`, same convention as subagent reports) and wakes a normal conversation turn, which relays in Sunny's voice with full thread context — or chooses silence. A `household`-audience run stays record-only (no wake, no text). The raw run output continues to land verbatim in `schedule_runs`, so the audit trail is unchanged. `durable-execution`'s carve-out ("direct terminal delivery … is reserved for scheduled runs") is deleted.
- **One voice layer.** A shared module derives, from a run's RunSpec, both halves of the speech contract: (a) the prompt block — who reads your final text, that it is delivered verbatim as one message, that a reply containing the silence sentinel delivers nothing, that inter-tool text is private, and that `(subagent)`/`(scheduled)`-labeled inbound messages are reports whose sender is *not* your reply's recipient (steer workers via `message`); and (b) the terminal parser — one `finalizeSpeech` (report-block extraction + sentinel + classification) replacing the three hand-rolled parsers in `conversation.ts` / `subagent.ts` / `scheduledJob.ts`. The three prompt builders keep only genuine framing differences (interactive / autonomous / child). Sentinel choice follows the lane: speakers (conversation) use `<no-reply/>`; reporters (all autonomous runs) use `<no-report/>`; presence-means-silence everywhere (the PR #73 semantics, now specced).
- **Audience replaces `outputTarget`, end to end.** Standing-schedule frontmatter gains an `audience:` key (`person:<name>` — the default, the creating subject — or `household` for silent pipeline jobs); the loader migrates legacy `outputTarget` frontmatter once and the field is retired. `schedule_create` gains a model-facing `deliver_to` parameter (a roster name, or `nobody` → household) and its description is rewritten around reports and the decision rule (artifact-producing job → `nobody`; message-producing job → a person, with conditional reporting). The DB `output_target` column derivation shim is confined to legacy one-shot rows.
- **One vocabulary, taught.** Tool descriptions, the delegation skill, and the generated voice block all use *audience* (who a run is for → whose conversation loop gets its report) and *authority* (what it may do) in the same words as the code. The delegation skill gains the silent-vs-delivering decision rule and drops language implying schedules text people directly.
- **Spec reconciliation.** `run-audiences` drops silence-by-grant-absence in favor of the audience-axis model the code follows, and legitimizes the sentinel as text-as-reply's structural silence convention; `messaging-gateway` syncs to presence-means-silence; `scheduling` and `tool-access` pick up reports-not-texts and the `deliver_to` surface.

## Non-goals

- No changes to the delivery bus internals, the authority/attenuation model, the gateway, the translator, or WDK plumbing.
- The `message` tool's deliberate fan-out (a household run briefing a roster member; a conversation relaying to Kate) remains direct gateway speech — mediating *addressed* messages through the recipient's loop is a follow-up only if it produces the same voice problems.
- No merging of the two sentinels into one token (the lane distinction is load-bearing in prompt language).
- No first-class `runs` table or RunSpec storage refactor.

## Impact

- Affected specs: `run-audiences`, `durable-execution`, `scheduling`, `tool-access`, `messaging-gateway`.
- Affected code: `src/agent/voice.ts` (new), `src/agent/prompt.ts`, `src/agent/delivery.ts`, `workflows/{conversation,subagent,scheduledJob,runShell}.ts`, `src/agent/tools/scheduleSpecs.ts`, `src/scheduler/index.ts` (frontmatter + migration), `agent/builtin/skills/delegation/SKILL.md`, `agent/builtin/schedules/dreaming.md`, dashboard schedule views.
- Live-state coordination at deploy: the four standing-schedule files (`heartbeat`, `task-assistant`, `craft-daily-resource-tagging`, `news-newsletter-processing`) get `audience:` frontmatter and report-shaped prompt tails; requires a devbox restart (Devon-approved window).
- Cost/latency: one extra conversation turn per delivered scheduled result (~27k effective cached input at current context-lifecycle numbers) — negligible at current schedule volume; silent jobs add nothing.
