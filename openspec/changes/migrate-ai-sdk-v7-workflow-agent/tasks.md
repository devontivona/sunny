## 5. Langfuse trace cleanup (D4 — source-confirmed the duplication PERSISTS in v7)

- [~] 5.1 Drive a live turn post-migration and INSPECT the trace (`langfuse-cli`): count `send_message`/`ai.streamText` spans vs runtime sends/steps to CONFIRM the source prediction. **BLOCKED by a NEW finding — durable turns emit ZERO telemetry under v7.** Drove a real-model durable turn live (sunny on v7 via devbox; loopback channel): the turn ran + delivered a real reply (run `completed`, message sent) — but NO Langfuse trace was produced (confirmed over multiple flush windows; only the standalone main-process smokes appear). Root cause: v7 moved telemetry from the OTel-global tracer to `ai`'s `registerTelemetry` registry, which is REALM-LOCAL; the WDK runs the durable orchestration in an isolated VM (own `globalThis` — confirmed by `@workflow/core` class-serialization's own comment) and steps in separate inlined-`ai` bundles, so `registerTelemetry` (called in the main process by `instrumentation.ts`) never reaches the `WorkflowAgent`. A per-call `telemetry.integrations: [new OpenTelemetry()]` override (tried + reverted) didn't help — the integration's `trace.getTracer('ai')` resolves to a no-op in a realm with no registered provider. So the spans are silently non-recording. v6 worked because it emitted via the OTel global API. **This blocks 5.1/5.4 and is an observability REGRESSION (durable traces vanished, not just duplicated).** Fix directions for a focused follow-up: register the OTel provider/integration INSIDE the step-bundle realm (steps run in real Node; `@opentelemetry/api`'s provider is process-global, so the `doStream` generation span could emit from a step) and/or inside the workflow VM for the agent-loop spans; or report upstream that `registerTelemetry` doesn't propagate to WDK workflow realms (relates to 5.3). The CORE migration is unaffected — durable turns work functionally (this is the **8.1 loopback live smoke, default-durable + real model: PASSING**).
